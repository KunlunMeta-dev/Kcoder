Create or read a managed visualization artifact (diagram, chart, map or adjustable recipe) for a Studio task. Studio-only: unavailable in CLI/TUI. It stores a private widget revision, not a project file, and does not install services, authorize accounts or verify correctness. Use it when a visual makes relationships, comparisons, trends or scenarios clearer; keep simple answers as text, and produce requested downloadable reports, images, decks or sites through their real artifact workflow. Always keep the explanation and conclusions in ordinary reply text: a stored artifact does not prove it was rendered.

- `action:"render"` (default): requires nonblank `title` (at most 256 UTF-8 bytes), plain-text `summary` (at most 4096 bytes) and complete `widget_code` (1 byte to 1 MiB); optional `format` (`html`/`svg`), `execution_mode`, `libraries` (`chart_js`, `d3`, `topojson`). A new widget omits `widget_id` and `expected_revision`; an update supplies both from the latest receipt. No read fields.
- `action:"read"`: exactly one of `widget_id` (add `expected_revision` only for a historical revision) or the original provider `lookup_tool_call_id` (optional `lookup_attempt_id`); optional `include_source` (at most 64 KiB, check `source_truncated`). No render fields. It returns stored metadata and the last render observation, not a fresh visual check.
- Never invent, placeholder or borrow IDs, revisions or call IDs; copy them from actual receipts. HTML/SVG element IDs inside `widget_code` are ordinary local identifiers.

`widget_code` is the original HTML/SVG string, JSON-escaped once in the outer arguments: no double encoding, wrapper objects or Markdown fences. Managed mode accepts passive SVG/static HTML plus inert declarations: a raw Chart.js 4.5.1 configuration in `<script type="application/json" data-kcoder-chart>` with `libraries:["chart_js"]` (core types only; at most 32 datasets and 10000 data entries per chart, 8 charts per widget); `<script type="application/json" data-kcoder-map>` whose `values` are keyed by ISO 3166-1 numeric codes, with `libraries:["d3","topojson"]`; and `data-kcoder-recipe="compound-interest"` holding a `data-kcoder-config` JSON object. No executable scripts, `new Chart(...)`, inline event handlers, network or external resources, or frames; the rendered DOM is bounded to 4000 nodes. Studio owns presentation and scrolling; no open/expand/focus argument exists.

In the final answer, put the saved reference on its own line outside code fences: the literal `::kcoder-widget{widget_id=`, the JSON-quoted `widget_id` from the successful receipt, ` revision=`, that receipt's numeric `revision`, and `}`. A receipt proves durable storage only, not correctness, rendering or user review.

Recovery: follow the error's reason and JSON pointer without coercing or inventing data. On a revision conflict, read the latest by `widget_id` before updating. After a lost or unknown render result, read by `lookup_tool_call_id` instead of rendering again. When an observation has `repair_allowed:true`, update only that widget, at most twice per task.
